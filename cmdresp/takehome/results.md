# NTT-256 accelerator: results

Batched forward NTT of 256-coefficient polynomials over Z_q, q = 8380417 (FIPS 204 /
ML-DSA), as a host-activated Vitis HLS kernel on the command-response pattern.  Built with
Waveflow following `examples/stream_inband`; part xc7z020clg484-1, 10 ns clock, Vitis HLS
2026.1 (`vitis-run`).  Rebuild everything with `python ntt_build.py --through summary`.

## Interface

**Streams.** `s_in` and `m_out` are 32-bit AXI4-Stream; AXI-Lite (`s_axi_control`) carries only
control and status.  Layouts below are from serializing schema instances
(`results/layout.md`), not from reading the schemas.

**Command header** (`NttCmdHdr`, 1 word).  Its TLAST is not inspected.

| Bits | Field | Meaning |
| --- | --- | --- |
| 7:0 | `cmd_type` | `NTT` = 1, `END` = 2; any other value (0 included) is `BAD_CMD` |
| 23:8 | `tx_id` | command ID, echoed in the response or reported on error |
| 31:24 | `nbatch` | polynomials in the batch, valid 1..16 (sent as 0 and ignored on `END`) |

Example: NTT, tx_id 0x1234, nbatch 16 = `0x10123401`; END = `0x00000002`.

**NTT command** = header, then `nbatch` input bursts, one per polynomial: 256 words, one
coefficient per word, the whole 32-bit word is the value (must be < q), TLAST on word 255.

**Response** to an NTT command = response header (`NttRespHdr`, 1 word, its own burst with
TLAST: `tx_id` bits 15:0, `nbatch` bits 23:16, e.g. `0x00101234`), then `nbatch` output
bursts in input order: 256 words, the coefficient in bits 22:0 and bits 31:23 zero, TLAST on
word 255.  `END` gets no response.

**Status registers** (AXI-Lite, from the S_AXILITE Registers table in `reports/csynth.rpt`; pragmas in
`gen/ntt.cpp`): `CTRL` 0x00 (ap_start / ap_done / ap_idle), `halted` 0x10 (1 = halted on
error), `error` 0x20 (code below), `tx_id` 0x30 (the failed command's tx_id), each with an
`_ctrl` ap_vld register at +4.  All three are cleared at the start of every activation.

| Code | Name | Raised when |
| --- | --- | --- |
| 0 | `NO_ERROR` | |
| 1 | `TLAST_EARLY` | TLAST on word k < 255 of a polynomial's input burst |
| 2 | `TLAST_MISSING` | word 255 of a polynomial's input burst has no TLAST |
| 3 | `BAD_PARAM` | `nbatch` = 0 or > 16 |
| 4 | `BAD_CMD` | `cmd_type` is neither NTT nor END |
| 5 | `BAD_COEFF` | an input word >= q |

**Host protocol.** Write `ap_start`; send commands, then `END`; wait for `ap_done`; read
`halted`, `error`, `tx_id`.  Expect one response header plus `nbatch` bursts per NTT command.
After an error, reset the stream path (the input may still hold words the kernel never read)
before the next `ap_start`.

## Design

`body()` in `ntt_body_impl.tpp` is one loop over commands (`CMDS`).  Per command it reads the
1-word header; returns on `END`; checks `cmd_type` then `nbatch` (BAD_CMD, then BAD_PARAM)
before writing anything; writes the response header; then loops over the polynomials
(`POLYS`), one at a time:

1. `load_poly` (loop `LOAD`, II = 1): reads 256 words into buffer `a`, checking each word for
   `>= q` (BAD_COEFF) before its TLAST (TLAST_EARLY), and stopping at the first bad word.
2. `ntt_transform` (loop `NTT_STAGES`): the 8 butterfly stages of FIPS 204 Algorithm 41,
   ping-pong between buffers `a` and `b` (a -> b -> a ...), so the result ends in `a`.  Each
   stage is `ntt_stage` (loop `STAGE_BFLY`, 128 butterflies): `t = zeta * v mod q`,
   `u + t`, `u - t`.  The twiddle factor of group g in stage s is `ZETAS[2^s + g]`, a 256-entry
   ROM (`ntt_zetas.h`).  `mulmod` reduces the 46-bit product with 2^23 = 2^13 - 1 (mod q):
   three shift-and-add folds and one conditional subtraction, so the only DSPs are the 23x23
   multiplier's.
3. `store_poly` (loop `STORE`, II = 1): writes `a` as one 256-word burst, TLAST on the last.

**State.** Only the two 256 x 23-bit buffers `a`, `b` (true dual-port BRAM), used within one
polynomial, and the status registers.  Nothing is kept between polynomials, commands or
activations.  Because a polynomial's output burst is written only after its input is complete
and checked, no output burst is ever open when an error is detected.

**Throughput: the target is not reached.**  The plan was one butterfly per clock (loop
`STAGE_BFLY` at II = 1), which needs each butterfly's two reads and two writes on separate RAM
ports: `ntt_stage` reads two words of one buffer and writes two of the other.  Vitis shared the
two `ntt_stage` call sites in one instance, and inside it both writes to `out` went through one
port ("Potential resource conflict between 'store' operation ... on array 'out_r'",
`results/cosim_output.txt`, HLS 200-2199), so the loop is at **II = 2**: about 265 cycles per
stage instead of about 138, and about 2,650 cycles per polynomial instead of about 1,650.
Per the run instructions this was reported, not reworked (Open Items).

## Verification

**The model's independent check** (`model_check.py`, output `results/model_check.txt`):
ALL PASS.

- Hand-computed examples: delta_0 -> all 1; (q-1) delta_0 -> all q-1; zero -> zero;
  delta_1 -> w_hat[0] = 1753, w_hat[1] = 8378664 and w_hat[2i+1] = q - w_hat[2i] for all i;
  delta_128 -> 4808194 for i < 128 and 3572223 for i >= 128.  PASS.
- Direct reference: the defining formula w_hat[i] = sum w[j] zeta^((2 brv8(i)+1) j) mod q in
  Python integers (no butterflies, no twiddle table), on 4 random polynomials, all q-1,
  alternating 0/q-1 and delta_255: exact match.  PASS.
- Convolution property, NTT(a*b mod X^256+1) = NTT(a) .* NTT(b), negacyclic product computed
  schoolbook, 3 random pairs: PASS.

**The checker rejects wrong outputs** (`results/checker_selftest.txt`): natural-order output,
an error path that does not halt, a partial polynomial left open after an early TLAST, a
kernel that drains its input after BAD_PARAM, and one output not reduced mod q: all
REJECTED.

## Assumptions

Places prompt version 1 was silent or ambiguous, and what this run chose:

1. **END's fields.**  The prompt does not say whether END's `tx_id` and `nbatch` matter.
   Chosen: both are ignored; an END with a nonzero `nbatch` is not an error.
2. **TLAST on headers.**  The prompt specifies TLAST only for the polynomial bursts.  Chosen:
   the command header is a fixed one-word message and its TLAST is not inspected, so a header
   with or without TLAST is accepted (as in `stream_inband`).
3. **The response header before a data error.**  The prompt says what is output for the
   polynomials before an error, not when the response header goes out.  Chosen: it is written
   as soon as the command header passes its checks, before any data is read, so a BAD_COEFF or
   TLAST_EARLY in polynomial 0 leaves the response header alone on `m_out`.
4. **How the latency targets are measured.**  "Co-simulation latency of that activation" was
   taken as Vitis's per-transaction latency in `result.transaction.rpt`: `ap_start` to
   `ap_done`, which includes reading the END header.
5. **"One butterfly per clock."**  Taken as II = 1 for the butterfly loop in the synthesis
   report, with pipeline fill and loop overhead per stage covered by the 1,700-cycle budget.
6. **Opcode 0.**  With NTT = 1 and END = 2, an all-zero header word is BAD_CMD rather than END,
   so a host that sends zeros by mistake gets an error instead of a clean return.
7. **Polynomials one at a time.**  Reading polynomial p+1 does not overlap transforming or
   writing polynomial p.  The prompt allows this.  It sets the throughput (Design).
8. **No pysim and one stream width** (32 bits): the course flow measures timing in
   co-simulation only, and the prompt names no other width.
9. **Scenarios added** beyond the prompt's list: `bad_cmd_zero` (Assumption 6),
   `tlast_missing_first` (the kernel must not read polynomial 1) and `coeff_and_missing` (the
   second precedence case the prompt names).

## Open Items

1. **Throughput targets missed (FAIL).**  The butterfly loop reaches II = 2, not 1, because
   Vitis shared the two `ntt_stage` call sites in one instance and gave its output buffer a
   single write port (HLS 200-2199 in `results/cosim_output.txt`).  The likely fix is to give
   each stage's output buffer two write ports, for example by writing the stage loops so each
   reads one buffer and writes the other directly instead of through a shared function.
   Not attempted in this run, per the instruction to report a missed target rather than
   rework the kernel.  Expected with II = 1: about 1,650 cycles per polynomial.
